# Sherlock Design System (设计标准)

This skill encodes the Sherlock design system extracted from the Figma file `KIbHrX8UbS92rt8kyCoEgG` (设计标准). Use it whenever output needs to look like a screen from products such as 社会面风险管控, 应龙 MVP, 知识库平台, or any Chinese-language enterprise admin / data dashboard with the same visual language.

## What this system looks like at a glance

- **Aesthetic**: Chinese B-side enterprise admin. Blue primary (#266EFF), generous whitespace, light gray page background, white containers with thin gray borders.
- **Header**: Solid blue (#266EFF) top bar with white text, product name on the left, user/notifications on the right.
- **Layout**: Left sidebar (white) with icon + text menu items, main content area on a #F5F7FA background, white card containers with `border: 1px solid #DDDDDD` and `border-radius: 8px`.
- **Density**: Medium. Buttons are 32px tall, inputs are 32px tall, table rows ~48px, header cells ~44px.
- **Typography**: Helvetica Neue/Helvetica/Arial → PingFang SC/Microsoft YaHei fallback stack. Base body text 14px/22px line-height, headings range `header-1` (32px) to `header-7` (14px). Keep to 3–5 font sizes per screen. Full scale in the "Typography" section below.
- **Icons**: 24×24px artboard (assumed default), four style variants — Outlined (default), Two Tone, Filled, State. Gray-scale icons use `--color-icon-0` through `-3`; document-type and status-dot icons keep their original brand/semantic colors. Full breakdown in "Icon System" below.
- **Grid**: 1440×820px canonical artboard, 1208px content area, 24-column grid with a fixed 12px gutter. Spacing scale is 4/8/12/16/24/32px (4pt base), with 20px as a sanctioned exception for special modules. Six named layout patterns for detail pages. Full breakdown in "Grid System" below.
- **Also covered**: Collapse, Tree (standalone, distinct from the dropdown-housed TreeSelect), Profile summary cards, SweetAlert (notification/confirm dialogs lighter than Modal), Result (full-panel outcome screens), and Skeleton (content-shaped loading placeholders) — added 2026-06 from a full pass over the Figma source's component library.

When in doubt, mimic the screenshots of 社会面风险管控 / 应龙 MVP / 知识库平台 — that is the target.

## The decision flow

1. **Identify the page type** the user is asking for: list page (most common), detail page, form page, dashboard with stats/charts, or report-style page with sources.
2. **Pull the right tokens and components** from the sections below. Never invent colors — use the tokens.
3. **Compose** using the layout templates in the "Page Layout Templates" section below.
4. **If implementing in code**, default to HTML+CSS with the tokens as CSS variables (see "Code starter" below). React/Tailwind variants are in the "Code Snippets" section below.
5. **If implementing in Figma**, the source file already has all 24 variables and 59 components defined — reference them by name like `Button/Primary/Default`, `Tag/Success/Default`, etc.

## Typography

> **Added 2026-06** from the official "通用 / 文字" spec PDF.

### Font family (字体家族)

Priority order for B-side products (numbers/English favor Mac-system fonts first): **Helvetica Neue → Helvetica → Arial** (English/numbers), then **PingFang SC → Microsoft YaHei UI → 微软雅黑** (Chinese).

Lock the font-family fallback stack at project start — font is the most foundational/atomic layer of a B-side page, so changing it later ripples across the entire design.

```css
font-family: -apple-system, "Helvetica Neue", Helvetica, Arial, "PingFang SC", "Microsoft YaHei", sans-serif;
```

- **macOS**: English → San Francisco, Chinese → PingFang SC
- **Windows**: English → Segoe UI, Chinese → Microsoft YaHei

### Font size system (字号)

Keep to **no more than 4 font sizes** per interface for visual cleanliness. Two accepted standards:

| Standard | 说明文字 | 正文 | 导航文字 | 大标题 |
|---|---|---|---|---|
| Option A | 12px | 13px | 14px | 16px |
| Option B | 12px | 14px | 14px | 16px |

The Sherlock system's recommended base is **14px with 22px line-height** as the anchor pairing for body text. Other scale steps can be defined freely per context, but a single system should keep its font-size scale to **3–5 sizes** (excluding showcase/marketing pages) to maintain restraint.

### Type scale & line-height (字阶与行高)

| Font size | 12 | 13 | 14 | 16 | 18 | 20 |
|---|---|---|---|---|---|---|
| Line height | 20 | 22 | 22 | 24 | 32 | 38 |

Line-height must be counted as part of the type element itself when measuring spacing (not added on top) — think of it as an invisible box wrapping the glyph.

### Font weight (字重)

Keep to **regular (400)** and **medium (500)** for most UI text. Use **semibold (600)** only for emphasis, primarily in English/number contexts.

| Weight | Value |
|---|---|
| Regular | 400 |
| Medium | 500 |
| Semibold | 600 |

### Text color by context (字体颜色)

On light backgrounds, the same gray scale applies across all font sizes (12/13/14/16px):

| Variable | Value | Usage |
|---|---|---|
| `--color-text-header` | `#222222` | Special emphasis/prompt scenarios — the darkest tier |
| `--color-text-0` | `#333333` | Standard primary text |
| `--color-text-1` | `#666666` | Secondary text |
| `--color-text-2` | `#999999` | Tertiary/auxiliary text |

### Recommended line-height by use case (字体行高的使用场景)

| 样式 | 字号 | 建议行距 | 使用场景 |
|---|---|---|---|
| 标准字 | 20px | 28px | 用于特殊提示场景 |
| 标准字 | 16px | 24px | 用于详情页面的标题名称 |
| 标准字 | 14px | 22px | 用于导航、标签页、分组标题等 |
| 标准字 | 13px | 22px | 用于正文信息展示 |
| 标准字 | 12px | 22px | 用于辅助说明文字 |

Prefer system-native fonts (Microsoft YaHei, PingFang SC, etc.) at build time, since browsers/users vary in installed fonts.

### Semantic text roles (语义角色)

- **Header**: title-level text that establishes hierarchy against surrounding content — e.g. the bold top text in an Alert, or the dark heading text on a Card.
- **Text**: body content inside most components — e.g. button labels, input values.
- **Paragraph**: multi-line block text — e.g. a textarea/paragraph input, often paired with a character counter (`0/150`).

## Icon System (图标)

> **Added 2026-06** from the official "通用 / 图标" spec PDF + source SVG sprite.
>
> **Note on artboard size**: the source PDF does not state a canonical artboard size — only stroke widths (1px / 1.4px). Per user decision, this skill assumes the **industry-standard 24×24px artboard**, scaled proportionally for the smaller in-component sizes already defined (e.g. 16×16px Checkbox/Radio, 16×16px SideMenu icon). Treat this as a default, not a confirmed spec value — flag if the Figma source defines something different.

### Style variants (风格变体)

The icon set ships in four rendering styles. Pick one per context — don't mix styles within the same screen/component group.

| Style | Stroke/fill | Typical use |
|---|---|---|
| **Outlined** | Line-based, stroke only, no fill | Default for most UI icons — nav, buttons, table actions |
| **Two Tone** | Line + a light secondary fill layer | Richer/illustrative contexts — empty states, onboarding, feature highlights |
| **Filled** | Solid fill, often in brand/semantic colors | Status indicators, badges, prominent call-to-action icons |
| **State** | Filled circular badges (colored dot/ring) | Status dots — success/warning/error/info indicators, similar role to the `Status` component |

### Stroke weight (描边规格)

| Token | Value | Usage |
|---|---|---|
| `icon-stroke-standard` | 1.4px | Default stroke weight for most Outlined icons at 24px artboard |
| `icon-stroke-fine` | 1px | Finer/smaller icons or dense UI contexts (e.g. inline table icons) |

### Color mapping (颜色)

**Outlined / Two Tone icons** — map to the existing icon gray-scale tokens, same tiering as everywhere else in the system:

| Variable | Value | Usage |
|---|---|---|
| `--color-icon-0` | `#999999` | Default icon color — most outlined icons at rest |
| `--color-icon-1` | `#C5C5C5` | Lighter/secondary icon tier (e.g. Two Tone's light fill layer) |
| `--color-icon-2` | `#DDDDDD` | Lightest tier — disabled icons, subtle decorative icons |
| `--color-icon-3` | `#FFFFFF` | Icon on highlighted/dark background (e.g. icon inside a Primary Button or on the TopNav) |

**Filled / State icons** — per user decision, these **keep their original multi-color palette** from the source set (red, orange, green, blue, purple, etc.) rather than being forced onto the system's semantic tokens. Reasons to keep them distinct: document-type icons (Word/Excel/PDF/PSD in the "Document" row) need to stay recognizable by their established brand colors, and State dots need a wider color range than the 4 semantic colors provide. When a Filled/State icon's color *does* happen to need to match a system semantic meaning (e.g. a green dot meaning "success"), prefer `--color-success` for consistency — but don't force it for icons whose color is identity-driven (logos, document types) rather than status-driven.

### Icon categories (图标分类)

The source set is organized into seven functional categories — useful for knowing what's available when picking an icon for a given UI role:

| Category | Count | Typical contents |
|---|---|---|
| 编辑类图标 (Editing) | 41 | Text formatting, headers H1-H6, alignment, lists, bold/italic |
| 方向指示类图标 (Directional) | 34 | Arrows, chevrons, carets — all directions |
| 影音类图标 (Media/AV) | 16 | Play, pause, skip, volume, fullscreen |
| 通用类图标 (General) | 80 | The largest catch-all category — calendar, folder, settings, common UI glyphs |
| 交互按钮类图标 (Interactive/Action) | 38 | Star/favorite, heart/like, share, comment, search, filter |
| 提示建议类图标 (Hints/Suggestions) | 17 | Info, question mark, checkmark, warning — feedback-adjacent glyphs |
| 面性图标 (Filled/solid glyphs) | 25 | Solid dot-based icons — volume, lock, music, more |

### Special icon sets (特殊图标组)

- **The drop-down**: a small dedicated set of icons used specifically inside dropdown/select triggers — distinct from general-purpose icons, don't substitute freely.
- **Document icons**: brand-colored file-type icons (Word blue, Excel green, PDF red, PSD blue, PPT orange, RAR/ZIP, folder). These intentionally don't follow the gray icon-token system — see "Color mapping" above.

### Usage rules (使用规则)

- Default to **Outlined** style for standard UI icons (buttons, nav, table row actions) unless the context calls for something more expressive.
- Don't mix Outlined and Two Tone icons in the same component group (e.g. don't have some sidebar icons Outlined and others Two Tone).
- Icon color should follow the gray-scale icon tokens (`--color-icon-0` through `-3`), matching the same hover/active logic as the text it sits beside — e.g. a `SideMenu/Item` icon uses `--color-icon-0` at rest and `--color-primary` when active, mirroring the text color rule already defined in Component specs.
- Document-type and State-dot icons are the only sanctioned exceptions to the gray-scale rule (see "Color mapping").

## Grid System (栅格系统)

> **Added 2026-06** from the official "通用 / 栅格系统" spec PDF.

### Canonical artboard size (统一的画板尺寸)

The recommended B-side design artboard is **1440×820px**. Reasoning behind this choice:

- Mainstream admin/dashboard pages today need to adapt across 1920 / 1600 / 1440 / 1366px screen widths (with some 1280px). 1440px sits in the middle of that range, so scaling up or down to other resolutions produces fewer broken/misaligned elements than designing at the extremes (e.g. designing at 1920 and then having it break on a client's actual 1024×720 environment — a real failure case from a past project).
- The 820px height comes from subtracting ~80px for browser chrome (tabs + address bar) from a 900px viewport.

**Don't assume 1920px is safe** just because it's common — narrower client environments are common in government/enterprise IT and 1440 degrades more gracefully.

### 24-column grid (24栅格体系)

Based on the 1440×820 artboard, using a 4pt grid as the base unit:

| Property | Value |
|---|---|
| Total columns | 24 |
| Content area width | 1208px |
| Gutter (槽/间隙) | 12px — **fixed**, never changes across breakpoints |
| Side margins (页边距) | 12px |
| Sidebar | Fixed width (`Fixed`), does not participate in the column grid |
| Content area | Fluid/responsive (`自适应`) — columns resize with viewport, but the gutter always stays 12px |

The grid's total width breaks down as **23 columns + 1 half-column = full content width**. Using 24 columns (rather than the more common 12) gives finer-grained, more flexible layout options — useful for the denser, more varied layouts this system's domain (government risk-management / case-management tooling) tends to need.

### Common column split patterns (常见分栏比例)

These are the standard ways to divide the 24-column grid for module layout:

| Split | Use case |
|---|---|
| 100% | Full-width single section (e.g. a wide table) |
| 80% / 20% | Main content + narrow side panel |
| 20% / 80% | Narrow side panel + main content (e.g. filters on the left) |
| 50% / 50% | Two equal-weight sections (e.g. two charts side by side) |
| 33.33% / 33.33% / 33.33% | Three equal-weight sections |

### Applied example (实践应用)

The 24-column grid in practice on a list page (e.g. 审批任务): sidebar is fixed-width, the content area (filter bar + tabs + table + pagination) spans the full 1208px content width as a single white card, with the table's internal columns (序号/标题/经办人/状态/操作 etc.) dividing that width as needed per the content, not strictly tied to grid columns.

### Spacing scale (间距)

The base unit is **4px**; the spacing system uses multiples of 4 to form 5 common spacing values:

| Token | Value |
|---|---|
| `spacing-1` | 4px |
| `spacing-2` | 8px |
| `spacing-3` | 12px |
| `spacing-4` | 16px |
| `spacing-5` | 24px |
| `spacing-6` | 32px |

**Exception**: special/dense modules may use a custom **20px** value (multiple of 4, but outside the 5 common steps) when the standard scale doesn't fit — e.g. card internal padding.

> **Note**: this replaces the prior spacing scale in the "Page Layout Templates" section below, which listed the same steps plus a less-precisely-justified 20px. The 2026-06 spec here is now authoritative.

### Layout patterns (布局规则 — six layout types)

Six base layout patterns cover the system's page-composition needs, primarily for detail-page module arrangement:

| Pattern | 中文名 | Typical use |
|---|---|---|
| Full-width (通栏) | 通栏 | High-volume paginated/tiled list components |
| Left-right (左右结构) | 左右结构 | Left tree + right list, or card layouts |
| Right-sidebar, top-left-right (右侧栏/上左右结构) | 右侧栏(上左右结构) | Detail pages: top profile summary + key-path/tree/related-list/card combinations |
| Left-sidebar (左侧栏) | 左侧栏 | Detail pages: top profile summary + form/card/related-list combinations |
| Three-column (三栏) | 三栏 | Detail pages: chart + form + related-list combinations |
| Two-column (两栏) | 两栏 | Detail pages: chart + form/related-list combinations |

When building a detail page, pick the layout pattern that matches the module mix the page actually needs (e.g. a case file with a chart and a form maps to "Two-column"; one with a chart, form, *and* related list maps to "Three-column"). Full-width and Left-right are the two most common patterns for list-style pages; the remaining four are primarily for detail pages.

## Component specs

Each component below lists its dimensions, padding, corner radius, and the tokens it uses. Use these specs verbatim — they're tuned to match the source designs. Token names below were migrated to the 2026-06 English variable names (see "Color tokens" above); `success`/`warning` tokens are unchanged pending the new spec.

### Basic components (基础组件)

**Button** — 32px tall (29 inner + border), padding `6px 16px`, radius `6px`, font 14px Regular
- `Button/Primary/Default`: bg=`--color-primary`, text=`--color-white`
- `Button/Primary/Hover`: bg=`--color-primary-hover`, text=`--color-white`
- `Button/Primary/Disabled`: bg=`--color-primary-disabled`, text=`--color-white`
- `Button/Default/Default`: bg=`--color-bg-container`, text=`--color-text-0`, border=`--color-border`
- `Button/Default/Hover`: bg=`--color-bg-container`, text=`--color-primary`, border=`--color-primary`
- `Button/Default/Disabled`: bg=`--color-fill-hover`, text=`--color-disabled-text`, border=`--color-border`
- `Button/Danger/Default`: bg=`--color-danger`, text=`--color-white`
- `Button/Text/Default`: bg=`--color-bg-container`, text=`--color-primary`, no border

**Tag** — padding `2px 8px`, radius `4px`, font 12px Regular. Several rendering styles share the same color logic (info=primary, success, warning, error, default/neutral, plus a purple accent seen in source for a 5th category) — pick one style per context, don't mix styles within the same list/table column.
- `Tag/Filled/Info|Success|Warning|Error|Default`: light bg + colored text — bg=`--color-primarylight-default`/`--color-success-bg`/`--color-warning-bg`/`--color-dangerlight-default`/`--color-fill-hover`, text=`--color-primary`/`--color-success`/`--color-warning`/`--color-danger`/`--color-text-1`. This is the default Tag style for most contexts.
- `Tag/Outlined/*`: same color logic as Filled but bg=`--color-bg-container` (white) with a 1px border in the matching color instead of a tinted background — a lighter-weight alternative when a screen already has a lot of color from tinted-bg tags elsewhere.
- `Tag/Bordered-Solid/*` *(compact variant)*: narrower padding, border only, no bg tint — seen in source as a denser "标 / 标" style abbreviated tag, for very tight table cells.
- `Tag/Icon/*`: same Filled color logic, with a small leading icon (e.g. a folder icon for a category tag, a status icon for a state tag) before the text, ~4px gap between icon and text.
- `Tag/Dot/*`: same color logic, with a small filled dot (4px) before the text instead of an icon — functions similarly to the `Status` component but rendered as a tag chip rather than inline text.

**Alert** — 380px wide, 40px tall, padding `10px 16px`, radius `6px`, 1px border, 8px dot on left + 14px text. - `Alert/Info`: bg=`--color-primarylight-default`, border+dot=`--color-primary`

**Message** (全局提示) — a lightweight, **auto-dismissing** toast-style notice, typically anchored to the top of the viewport. This is the key distinction from `Alert`: Message is transient and floats above content rather than living inside the page flow.

- **Dialog form**: a heavier variant housed in a small floating card (bg=`--color-bg-container`, border=`--color-border`, radius `6px`, shadow `0 4px 16px rgba(0,0,0,0.1)`) with a status icon + title (14px Medium) + close ✕ in the header row, optional body text below (`--color-text-1` 14px, supports multi-line/long-form content), and a footer with `Button/Default/Default` ("取消") + `Button/Primary/Default` ("确定") when the notice requires explicit user action rather than passive dismissal. This form sits between a plain `Message` and a full `Modal` — use it for quick confirmations that don't need the heavier modal treatment (e.g. "确定操作" with a one-line description), reserving `Modal` for content-heavier or higher-stakes confirmations.

- Body: padding `24px`, content 14px `--color-text-0`
- Footer: padding `12px 24px`, 1px top border, right-aligned Cancel + Confirm buttons
- **Destructive confirm variant**: same structure, but the Confirm button uses `Button/Danger/Default` instead of `Button/Primary/Default` when the action is destructive/irreversible (e.g. "确定删除数据吗?"), and the body text should explain the consequence plainly (e.g. "该数据删除后将无法找回，请谨慎操作，必要时可联系管理员寻求帮助").

**Popconfirm** (气泡确认框) — a small inline confirmation popover anchored directly to the triggering element (e.g. a "删除" link in a table row), avoiding the heavier full-screen-centered feel of a `Modal` for low-stakes/easily-reversible confirmations.
- Card: bg=`--color-bg-container`, border=`--color-border`, radius `6px`, shadow `0 4px 16px rgba(0,0,0,0.1)`, padding `12px 16px`, with a small triangular pointer connecting it to the trigger (same positioning model as `Tooltip`/`Popover`).
- Content: a single confirmation question (`--color-text-0` 14px, e.g. "你确定要删除这次任务吗?") followed by right-aligned `Button/Default/Default` ("取消") + `Button/Primary/Default` ("确定") — both buttons sized smaller than their standard 32px-tall spec (closer to ~28px) to fit the compact card.
- Use Popconfirm instead of a destructive `Modal` when the action is low-stakes or easily undoable; reserve the `Modal` destructive variant for higher-consequence/irreversible actions.

**Notification** (通知提醒框) — a richer, longer-lived toast than `Message`, anchored to a screen corner (commonly top-right) rather than top-center, intended for background/async event reporting (e.g. a completed export, a system warning) rather than direct response to an immediate user action.
- Card: ~360px wide, bg=`--color-bg-container`, border=`--color-border`, radius `6px`, shadow `0 4px 16px rgba(0,0,0,0.1)`, padding `16px`.
- Layout: status icon (20px, semantic color) at top-left + title (14px Medium, `--color-text-0`) + close ✕ top-right, description text below (`--color-text-1` 14px, can wrap multi-line) + a trailing "我知道了"-style action link (`--color-link`) bottom-right.
- Variants: `Notification/Success` (✓ `--color-success`), `Notification/Error` (✕ `--color-danger`), `Notification/Warning` (⚠ `--color-warning`) — same icon-color logic as `Message`, but Notification always keeps the bordered-card treatment (no plain/compact form) since it's meant to be noticed even when the user isn't actively looking at that part of the screen.

**Drawer** (抽屉) — a panel that slides in from the screen edge (typically right) over the existing content, used for secondary tasks/detail views that don't warrant a full page navigation or the more disruptive center-screen feel of a `Modal`.
- Panel: bg=`--color-bg-container`, full height, width varies by content density — source shows both a ~360px narrow form-drawer and a ~600px wide content-drawer side by side, so width should match the complexity of the drawer's content rather than a single fixed value.
- Header: padding `16px 24px`, 1px bottom border, title 16px Semi Bold (`--color-text-0`) + close ✕ (`--color-icon-0`) top-right.
- Body: padding `24px`, scrollable if content overflows, bg slightly different from the page (`--color-fill-hover`-tinted) to distinguish drawer body from header/footer.
- Footer: padding `12px 24px`, 1px top border, right-aligned `Button/Default/Default` ("取消") alone, or paired with `Button/Primary/Default` ("保存"/"确定") when the drawer collects input rather than just displaying content.
- **Stacked drawers**: source shows two drawers open simultaneously, offset slightly — supports a secondary drawer opening on top of a primary one (e.g. drilling into a sub-detail from within a detail drawer) rather than replacing it.

**Tooltip** — black 85% opacity bg, white text 12px, radius `4px`, padding `6px 8px`. Supports positioning on any of 8 sides relative to the trigger (top/bottom/left/right, plus the 4 corner-aligned variants), each with a small triangular pointer connecting the tooltip to its trigger element on the matching edge.

**Loading** — animation speed is **150ms** per the source spec; export the component as a PNG sequence when handing off to engineering, rather than relying on a CSS-only spinner if frame-accurate timing matters. Three visual styles, each available in a few rotation/fill states for a multi-frame animation:
- `Loading/Circular`: 32×32 circular spinner, track=`--color-primarylight-default` 3px stroke, indicator dot/arc=`--color-primary` — the default style, matches the existing spec.
- `Loading/Radial-burst`: a radial "starburst" of short blue lines around a center point, with one or two lines highlighted brighter (`--color-primary`) per frame to suggest rotation — a denser/busier alternative to the circular spinner.
- `Loading/Bar-pulse`: a horizontal cluster of short vertical bars, one bar per frame rendered taller/bolder (`--color-primary`) than its neighbors (`--color-primarylight-default` or `--color-border`) to suggest a pulsing/scanning motion — useful for a more compact inline loading indicator (e.g. inside a button or small card).

**Skeleton** (骨架屏) — content-shaped gray placeholder blocks shown while real data is loading, an alternative to `Loading`'s spinner for content-heavy areas where showing the eventual layout shape reduces perceived wait time. Bg=`--color-fill-hover` (or `--color-border`-toned) rectangular blocks matching the shape of the content that will load in (text lines, avatar circle, button shape) — no spinner animation, optionally a subtle shimmer/pulse effect on the gray blocks themselves.
- Configurable parts (toggle independently per the content being loaded): an avatar-circle placeholder (left), one or more text-line bars of varying width (simulating title + body lines), and a button-shaped placeholder block — height grows from ~80px (text only) to ~160px (avatar + text + button all present) depending on which parts are enabled.
- Use Skeleton for card/list/profile-style content that's about to load with a known shape; use `Loading`'s spinner for actions/operations with no predictable content shape (e.g. a button mid-submit, a full-page transition).

**Empty** — 320×200 centered, gray placeholder rect 64×48 + text "暂无数据" 14px `--color-disabled-text`. This generic version is a fallback; prefer the scenario-specific illustrated variants below when the context is known:
- `Empty/暂无数据`: ~92×92px flat-line illustration (open box/drawer motif), line color `--color-icon-1`-family grays (`#EFEFEF`/`#E6E6E6`/`#E0E0E0`), small `--color-primary` accent dot/detail. Caption "暂无数据" 14px `--color-disabled-text` below. Use for an empty table/list/grid with no records at all.
- `Empty/暂无消息`: ~92×92px illustration (bell/notification motif with closed eyes — "nothing to report"), same gray palette + `--color-primary` accent, dark accent line in `--color-text-0`. Caption "暂无消息". Use for an empty notification/message list.
- `Empty/检索为空`: ~92×92px illustration (magnifying glass/search motif with closed eyes), same palette. Caption "检索为空". Use specifically when a search/filter query returns zero results — distinct from `暂无数据`, since here data exists but the current query excludes all of it (pairs well with a "清空筛选" prompt nearby).
- `Empty/暂无结果`: a larger, more elaborate 212×200px illustration (a seated person reviewing a clipboard/document — a more "considered" illustration style vs. the other three's simple line icons), accent colors `--color-primary` + `--color-primarylight-default`. Caption "暂无结果". Use for a more prominent/standalone empty state (e.g. a full-page or full-panel empty result), where the other three are typically smaller inline empty states within a card or list area.
- All four scenario variants share the same caption typography (14px, positioned ~16px below the illustration) — only the illustration and caption text change per scenario.

**ProgressIndicator** (关键路径) — horizontal multi-stage progress tracker for a named process (e.g. a project's key milestones), distinct from `Steps` (which is for in-progress multi-step forms/flows) — ProgressIndicator is for milestone/checkpoint tracking with richer per-node status.
- Header: process/project name (`--color-text-0` 14px Medium) + an info-tooltip icon (?) on the right.
- Nodes: a horizontal row of circular markers connected by a line, each with a label above (`--color-text-0` 14px) and a date below (`--color-text-1` 12px). Node states:
  - `ProgressIndicator/Node/Complete`: filled `--color-success`, connecting line to it also `--color-success`
  - `ProgressIndicator/Node/Error`: filled `--color-danger`, connecting line to it `--color-danger` — represents a milestone that failed/was rejected, distinct from simply "not yet reached"
  - `ProgressIndicator/Node/Current`: filled `--color-warning` with a larger outer ring (~2x the node's own radius) in `--color-warning` at reduced opacity, to draw attention to the active node — can apply to more than one adjacent node if a stage spans multiple current checkpoints
  - `ProgressIndicator/Node/Upcoming`: outline only, `--color-disabled-border`, connecting line to it also `--color-disabled-border`
- Below the node row, an optional content panel (light blue `--color-primarylight-default` background, centered "替换内容" placeholder text in `--color-link`) — used to show details relevant to the currently-selected node.

**SweetAlert** (弹窗提示) — a centered modal-style alert/confirm dialog, heavier and more illustrated than `Message`'s dialog form or `Popconfirm`, lighter than a full custom `Modal`. Two sub-families:
- `SweetAlert/Notification`: 400px wide, bg=`--color-bg-container`, radius `4px`, for passive status announcements. Scenarios: `场景=提示` (info), `场景=警告` (warning), `场景=成功` (success), `场景=错误` (error) — each pairs a large status icon (semantic color matching the scenario) with a title + description, optionally a "多行" variant that grows taller (~480px) for longer descriptions vs. the compact ~188px single-line form.
- `SweetAlert/Confirm`: 400px wide, same container styling, for action confirmation rather than passive notice. Scenarios: `场景=确认提示` (~166px, neutral confirm) and `场景=删除提示` (~188px, destructive — pairs with `Button/Danger/Default` for the confirm action, same destructive-styling rule as `Modal`'s destructive variant).
- Use `SweetAlert` over a full `Modal` when the dialog is a single self-contained message/confirmation without a complex form body; reach for `Modal` once the dialog needs arbitrary structured content beyond an icon + title + description.

**Result** (结果页) — a full-width/full-panel outcome screen shown after a multi-step process completes (e.g. after submitting a long form or finishing a task flow), distinct from `SweetAlert`/`Message` which are transient overlays — Result occupies the main content area itself.
- Base variant: 600px wide content block, large centered status illustration/icon + title + description, 218px tall per status. Four states: `类型=成功提示`, `类型=错误提示`, `类型=进行中` (in-progress, no error/success connotation), `类型=警告提示`.
- Richer "产建" variant: 420px wide, bg=`--color-bg-container`, radius `4px`, ~302px tall — adds space for a structured next-steps area below the status message (vs. the base variant's message-only layout).
- Supporting "详情字段" element: a small stat-card grid (119px wide columns, bg=`--color-fill`-toned `#F3F4F9`-family, radius `4px`) for showing 1–4 key result metrics alongside the main status (e.g. "处理耗时"/"成功数量") — height grows from ~38px (1 metric) to ~116px (4 metrics) by stacking rows.

### Navigation (导航组件)

> **Expanded 2026-06** from the official "通用 / 导航" spec PDF, covering PageHeader/Breadcrumb, Menu, Steps, Pagination, and Dropdown in more detail.

**TopNav** — 1200×56px (full width), padding `12px 24px`, logo + title on left, user/notification icons on right. Two sanctioned variants — pick one per product, don't mix within the same screen:
- `TopNav/Blue`: bg=`--color-primary` (or a subtle gradient using `--color-primary` → `--color-primary-hover`), title/icons=`--color-white`. Default for most product shells (matches 社会面风险管控 etc.)
- `TopNav/White`: bg=`--color-bg-container`, 1px bottom border=`--color-border`, title=`--color-text-0`, icons=`--color-icon-0`. Use for a lighter/quieter shell when the blue bar would compete with content below it.

**PageHeader / Breadcrumb** — sits directly under or inside the TopNav, showing hierarchy context. Three rendering contexts seen in the source:
- **On `TopNav/Blue`**: breadcrumb text in `--color-white` at reduced opacity (~70%) for parent segments, full-opacity `--color-white` for the current segment, separated by `/`.
- **On `TopNav/White`**: parent segments `--color-text-1`, current segment `--color-text-0` Medium, separator `/` in `--color-disabled-text` — same convention as the standalone `Breadcrumb` component below.
- **Dark/dropdown-panel context** (e.g. a breadcrumb history list shown in a dark popover): bg near-black, text `--color-white` at full opacity for the active row, dimmed for inactive rows. This is a contextual variant, not a separate token set — reuse `--color-overlay-bg`-adjacent dark tones rather than inventing a new dark palette.

**Breadcrumb** (standalone, on light background) — items separated by `/` in `--color-disabled-text`, current item `--color-text-0` Medium, previous items `--color-text-1` Regular, 14px.

**Menu (SideMenu)** — left sidebar navigation, supports nested levels and a collapsed icon-only state.

- `SideMenu/Item` — 240×44px, padding `12px 24px`, 12px gap between icon (16×16) and text (14px)
  - `SideMenu/Item/Default`: bg=`--color-bg-sidebar`, icon=`--color-text-1`, text=`--color-text-0` Regular
  - `SideMenu/Item/Active`: bg=`--color-primarylight-default`, icon=`--color-primary`, text=`--color-primary` Medium
  - `SideMenu/Item/Hover`: bg=`--color-fill-hover`, icon=`--color-text-1`, text=`--color-text-0` Regular
- `SideMenu/Item/Expandable` — same as `Item` but with a chevron on the right that rotates 90° when expanded. Clicking reveals child items indented below it.
- `SideMenu/SubItem` *(default values — not explicitly labeled with exact px in the source, inferred from the parent item's 44px/24px proportions; treat as a starting point, confirm against the live Figma file if precision matters)*: ~36×40px, indented an additional 24px from the parent's left edge (so ~48px total left padding), text 14px Regular, same color states as `SideMenu/Item` (default/active/hover use the same token mapping, just no icon).
- `SideMenu/Collapsed` — icon-only rail, ~64px wide, items show only the 16×16 icon centered, no text label. Tooltip on hover reveals the full label. Active/hover color states are identical to the expanded version (icon-only state changes layout, not color).
- Footer area (bottom of sidebar): user avatar (40×40, see `Avatar/Circle/Default`) + name, plus a settings gear icon — present in both expanded and collapsed states.

**Steps** — horizontal step indicator for multi-stage flows (e.g. a multi-step form/approval flow). Three visual states per step:
- `Steps/Step/Done`: circular marker filled `--color-primary` with a white checkmark (✓), label text `--color-text-0`, optional description below in `--color-text-1` 12px.
- `Steps/Step/Current`: circular marker filled `--color-primary` with the step number in white, label `--color-text-0` Medium (bolder than other states), description `--color-text-1` 12px.
- `Steps/Step/Upcoming`: circular marker outlined only (`--color-border`, no fill), number in `--color-disabled-text`, label `--color-disabled-text`, no description or dimmed description.
- Connector line between steps: `--color-primary` for the segment leading into a Done/Current step, `--color-border` for segments still upcoming.
- Steps also support a **progress-bar variant** for linear/non-numbered flows: a horizontal track (`--color-border`) with a filled portion (`--color-primary`) up to the current position, labeled segments below it as "已完成 / 进行中 / 未开始" in the same color logic as the numbered variant.

**Dropdown** — trigger + floating panel, used standalone (e.g. a city/region picker) or as the control inside `Select`.
- Trigger: same visual spec as `Select/Default` (280×32px, border=`--color-border`, radius `6px`) with a downward chevron icon on the right.
- Panel: bg=`--color-bg-container`, border=`--color-border`, radius `6px`, shadow `0 4px 16px rgba(0,0,0,0.1)`, padding `4px` around a list of options.
- Option row: padding `8px 12px`, text=`--color-text-0` 14px
  - `Dropdown/Option/Default`: bg=`--color-fill`
  - `Dropdown/Option/Hover`: bg=`--color-fill-hover`
  - `Dropdown/Option/Selected`: bg=`--color-fill-selected`, text=`--color-primary` Medium, optional checkmark on the right
- **Multi-column / cascading variant**: multiple option columns shown side-by-side in one panel (e.g. province → city), each column same width, separated by a 1px `--color-divider` vertical line. Used for hierarchical selection without leaving the dropdown.
- **Multi-select variant**: option rows show a `Checkbox` on the left instead of (or alongside) the trailing checkmark; selected options can optionally render as removable `Tag`s back in the trigger field.

**Tab** — padding `12px 16px`, 8px gap to indicator
- `Tab/Active`: text=`--color-primary` Medium 14px, 32×2px bottom indicator=`--color-primary`
- `Tab/Default`: text=`--color-text-0` Regular 14px, no indicator
- **Overflow behavior**: when the number of tabs exceeds the available row width, the trailing tabs collapse into a "更多 ⌵" trigger (`--color-text-0` 14px + chevron `--color-icon-0`) that opens a `Dropdown`-style list of the hidden tab labels (`选项一`/`选项二`/etc.) — keeps the visible tab row from wrapping or overflowing.

**Link** — 14px `--color-link`
- `Link/Default`: no underline
- `Link/Hover`: underline

## Don't-dos (common mistakes)

- **Don't invent colors.** Even close approximations like `#1677FF` or `#1890FF` are wrong now — the system was updated to `#266EFF` as primary. Always use the current token values.
- **Don't use Material/Bootstrap defaults** (shadows everywhere, big rounded corners, vibrant colors). This system is minimal, blue-and-gray, with thin borders and small radii (4–8px).
- **Don't add heavy shadows** to cards. They have a 1px `#DDDDDD` border instead. Only modals get a shadow.
- **Don't use English-only placeholder text** when building Chinese admin UIs — use 请输入, 请选择, 搜索任务名称, 暂无数据, etc.
- **Don't make rows too tall** in tables — header is 44px, rows are 48px. Going to 60+ breaks the density feel.
- **Don't center text in table cells by default** — left-align text columns, right-align number/amount columns.
- **Don't use a vivid red sidebar/header** — the top bar is always blue `#266EFF`, the sidebar is white.
- **Don't skip the breadcrumb** on detail pages — they typically have one (e.g., "资料库 / 报告生成").

### Grid system reference (layout context — see "Grid System" above for full spec)

The canonical artboard is **1440×820px** — content area 1208px wide, 24-column grid, 12px fixed gutter, 12px side margins. Sidebar is fixed-width and sits outside the grid; the content area is fluid. Full breakdown (column-split patterns, the six layout types) is in `SKILL.md` under "Grid System".

### Spacing scale (layout reference — see "Spacing scale (间距)" in Grid System for the authoritative source)

> **Updated 2026-06** from the official "通用 / 栅格系统" spec PDF — this table is now authoritative (see `SKILL.md` → "Grid System" → "Spacing scale" for source detail).

Base unit is 4px; use these 5 common steps:
- `4px` — within tight controls
- `8px` — between icon and text, between tag groups
- `12px` — between form rows, between menu items
- `16px` — section internal padding edges
- `24px` — header padding, modal padding
- `32px` — between major sections

Special/dense modules may use a custom `20px` (e.g. card internal padding) when the standard scale doesn't fit — this is an explicit exception, not part of the 5 common steps.

| Card title | 16px | Semi Bold |

| Body / table cell / input | 14px | Regular |
| KPI value | 24px | Semi Bold |

### Tips for editing the Figma file

- **Always bind colors via variables**, not hex literals. Use `figma.variables.setBoundVariableForPaint(...)` so the design stays consistent with the token system.
- **Don't bind variables to page backgrounds** — Figma's API rejects that. Use a Frame container as a backdrop instead.
- **Search before recreating.** Use `Figma:search_design_system` with a query like "Button Primary" to find existing components first.
- **Font names.** "Inter" weights are written with spaces: `Semi Bold`, `Extra Bold`, not `SemiBold`/`ExtraBold`.
- **Use `await figma.setCurrentPageAsync(page)`**. Assigning to `figma.currentPage` is not supported.
- **Page loading.** Use `await page.loadAsync()` per page when traversing — there is no `loadAllPagesAsync`.
